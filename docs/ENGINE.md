# Engine design (MacroSIPCore)

The engine is the only code that talks to PJSIP. The UI never imports `CPJSUA`.

## Threading model
- PJSIP demands that every `pjsua_*` call comes from a thread registered with `pj_thread_register`, and that its callbacks are not blocked.
- `Engine` is a Swift `actor` whose executor is a dedicated serial `DispatchQueue("macrosip.engine")`. The queue's thread registers itself with PJSIP on first use (`pj_thread_register` guarded by a thread-local flag). All `pjsua_*` calls run inside the actor.
- PJSIP callbacks (`on_reg_state2`, `on_incoming_call`, `on_call_state`, `on_call_media_state`, `on_call_transfer_status`, `on_buddy_state`, `on_dtmf_digit2`...) run on PJSIP worker threads. They copy the minimal data into an `EngineEvent` value and hand it to `Engine.events` (an `AsyncStream<EngineEvent>`), returning immediately. They never call back into the actor synchronously and never touch UI.
- `pjsua_config.thread_cnt = 1` and `cb` struct set once in `start()`. No `pjsua_handle_events` polling; the worker thread does it.
- Audio device changes (`pjsua_set_snd_dev2`) also happen inside the actor.

## Dial strings
`DialString.parse(_ raw: String, account: AccountConfig) -> DialString` yields a full SIP URI:
- `sip:user@host` / `sips:` → used as is.
- `tel:+7495...` → digits only, then `sip:<digits>@<domain>`.
- `100`, `+7 (495) 123-45-67`, `*72` → strip spaces, parens, dashes; `sip:<result>@<domain>`; transport parameter appended if the account uses TCP/TLS.
- Anything containing `@` without a scheme → prefix `sip:`.
Pure Swift, tested.

## Ringtone and ringback
- Incoming: `pjsua_player` with the ringtone WAV looped to the ringtone device (separate `pjmedia_snd_port` if the device differs from the call output). Stops on answer/decline.
- Outgoing early media absent: generate ringback tone with `pjmedia_tonegen` connected to the speaker.
- Incoming while another call is connected (`.callWaiting`): the call-waiting tone replaces the ringtone (see "Call options").

## Storage (MacroSIPCore, no PJSIP)
- `JSONStore<T: Codable>`: atomic write to `~/Library/Application Support/MacroSIP/<name>.json` (`FileManager.replaceItemAt`), load with default on missing/corrupt (corrupt file renamed `.broken-<timestamp>`).
- `AccountStore`, `ContactStore`, `CallLogStore`, `SettingsStore` wrap it.
- `Keychain`: `set(password:for: AccountID)`, `password(for:)`, `delete(for:)`; service `com.hsmm.macrosip` (so accounts carry over), account = UUID string.

## Error handling
`EngineError.pjsip(status: Int32, message: String)` built from `pj_strerror`. Every `pjsua_*` return value is checked. Errors never crash the engine; a failed registration becomes `RegistrationState.failed`.

## Tests (Swift Testing)
- DialString parsing table.
- JSONStore round trip, corrupt file recovery.
- Keychain with a test service name.
- Auto-answer rules (`AutoAnswerPolicy.decide(call:, contacts:, settings:) -> delay?`).
- Engine smoke: start, add an account with `enabled=false`, list codecs, stop (no network).

## Implementation notes (milestone 2)
Code: `Sources/MacroSIPCore/Engine/` (Engine, EngineBridge, EngineTypes, AccountMapping, PJSupport, TonePlayer, AudioDeviceWatcher), C helpers in `Sources/CPJSUA`, manual phone `macrosip-cli` (`--selftest` runs the localhost call check).

- **Executor and threads.** `Engine.unownedExecutor` is a `DispatchSerialQueue("macrosip.engine")`. GCD may run it on different pool threads, so every entry point calls `cpjsua_thread_register()` (C11 `_Thread_local pj_thread_desc`, no-op once registered, re-registers after a pjsua restart).
- **Callback bridge.** pjsua callbacks are C function pointers without context, so they are global Swift functions that reach the engine through `EngineBridge.shared` (a `Sendable` class over `OSAllocatedUnfairLock`; no `nonisolated(unsafe)`). A callback reads PJSIP data, updates the registry, yields the event and, when the engine must act (conference wiring, ringtone, hang-up after transfer), schedules `Task { await engine.… }`. Follow-up work is idempotent (reconcile current state), so its ordering does not matter.
- **Events.** Single consumer. They are yielded from PJSIP threads and the actor, so the UI iterates on `@MainActor`. `CallID` is `(raw: pjsua slot, serial)`: slots are reused, serials never are, and a stale `CallID` throws `.noSuchCall`. Upsert UI rows on `.incomingCall`/`.callChanged` (the first `.callChanged` of an outgoing call can arrive before `makeCall` returns) and remove them on `.callEnded`. A fifth incoming call gets 486 and appears only as `.callEnded(... .disconnected(code: 486 ...))`. Incoming calls stay `.incoming` while ringing (pjsua state EARLY after the automatic 180). `.callEnded` repeats the last codec/SRTP state and `duration` is the connected time (0 if never answered). `CallState.held` means local hold (`isOnHold`); remote hold stays `.connected`.
- **Deviations / additions.** `CallID` gained `serial`. `CallDirection` is the call-log enum from `Model/CallLogEntry.swift` (it also has `missed`, never produced by the engine). `Engine.init` takes `nullAudio` and `bindAddress` (bind SIP and RTP to one address; needed for localhost calls when the default route is a VPN). Additive API: `mediaStats(_:)`, `localPort(of:)`, `setRingtoneFile(_:)` (hook for the bundled WAV; nil = generated tone), `silenceRingtone()`, `inputLevel()`. `EngineError` has more cases than `.pjsip`. Conference, recording and presence members were stubs (`.unsupported`) until milestone 5; see below.
- **PJSIP specifics.** Calls are audio-only with `txt_cnt = 0`; the pjsua default offers an RFC 4103 text m-line that breaks un-hold. RTP ports come from `NetworkSettings.rtpPortStart`/`rtpPortCount` (default 4000-4999), the first pair randomized inside the window. VAD is off. Codec priorities start at 254 because PJSIP demotes 255 and creates a tie; unlisted codecs get 0 (disabled). After a successful transfer (final 2xx NOTIFY) the engine hangs up the transferred leg. `updateAccount` uses `disable_reg_on_modify` and re-registers explicitly. The old binding is not un-REGISTERed when the registrar changes; it expires on the server.
- **Review fixes (milestone 2.1).**
  - TLS: two listeners. The default one verifies the server: the macOS system roots are exported at `start` to `Application Support/MacroSIP/ca-roots.pem` (path injectable) for OpenSSL, and PJSIP sets SNI and checks CN/SAN against the request's destination host. Accounts with `AccountConfig.verifyTLSCertificate == false` (decodes as `true` from older JSON) use the second, non-verifying listener and get a `.log` warning. If the export fails, verification fails closed.
  - Registration: switching off never throws because of the registration's own state. PJSIP's "nothing registered" (`PJ_EINVALIDOP`) means done; "transaction in flight" (`PJSIP_EBUSY`, either direction) is remembered and repeated when the transaction completes. `updateAccount` always applies the new configuration. `addAccount` validates the id, registrar and proxy URIs with `pjsua_verify_sip_url` and rolls back if the registration cannot start. A 2xx without Expires counts as registered for the account's interval.
  - Calls: `CallID` serials continue across stop/start. Engine-side updates (`setMute`, `setHold`, `calls()`) never create call records, and call events are yielded inside the bridge lock, so no `.callChanged` follows a call's `.callEnded`. Conference wiring tracks the last requested state, because PJSIP 2.17 queues (dis)connections until the next audio frame.
  - Audio devices are remembered by name (`setAudioDevices(inputName:outputName:)`, `setRingtoneDevice(name:)`; the index variants store names too) and re-resolved after every device-list change.

## Implementation notes (milestone 5)
Code: `Engine+Conference.swift` (merge/split and the conference bridge wiring), `Engine+Recording.swift`, `Engine+Presence.swift`; bridge additions in `EngineBridge.swift`; `SignallingSource` in `PJSupport.swift`; C helpers in `Sources/CPJSUA` (recorder create/destroy-and-wait, buddy snapshot and token, NOTIFY body scan, presence publish, Call-Info parser, packet source). Public signatures are unchanged; `CallInfo.inConference`, `isRecording` and `answerAfter` are now filled. Additive public API: `Engine.recordingIsEmpty(_:)`. Changed 2026-10-12 for stereo recording: `startRecording` takes `layout:` (default `.mono`), `stopRecording` returns `RecordingFiles` (was `URL`), new `recordingFiles(of:)`, `RecordingLayout`/`RecordingFiles` in `EngineTypes.swift`, `RecordingConverter.convert(files:to:)`.

- **Conference model.** A conference is a group id in the bridge's `CallRecord.conference` (`inConference = conference != nil`, announced with `.callChanged`). `merge(ids)`: 2...`maxConcurrentCalls` distinct ids, each live (stale -> `.noSuchCall`) and CONFIRMED (`.connected`/`.held`; ringing, dialling, connecting -> `.invalidArgument`). Held legs are resumed first (re-INVITE with `PJSUA_CALL_UNHOLD`); they join the mix once their media is active again. A leg that is already in a conference brings its conference along (the lowest id survives). `split(id)` clears the flag on that leg; a conference left with one leg is dissolved (that leg gets `inConference == false` too). The same happens when a leg ends: with 3+ legs the others stay joined, the last remaining leg leaves. The split leg keeps microphone and speaker; holding it is the UI's decision. `merge`/`split` rewire the bridge even when they throw half-way.
- **Bridge wiring is one desired-state reconcile** (`reconcileMedia()`, replaces the per-call version). From all live calls and recordings it computes the wanted connections and diffs them against `requestedWiring`: per leg with media up (active or remote hold) leg->speaker, mic->leg unless muted; conference legs with media up transmit to each other both ways; a recorder gets its call, that call's conference partners and the mic (unless the recorded call is muted). A leg on local hold (or without media) is connected to nothing, but keeps its conference membership. `slotOwners` remembers who owned each conference slot; requests for a slot whose owner changed or vanished are forgotten (PJSIP dropped them with the port), which keeps slot reuse safe. Tone players connect themselves and are not touched.
- **Recording.** `pjsua_recorder_create` (WAV, 16-bit PCM mono at the conference clock rate, 16 kHz by default; the file name must end in `.wav`), parent directory created, existing file overwritten, one recorder per call. Nothing is written while the call is held; the mic is left out while muted. A file that only has the 44-byte header (held all the time) is still returned; `Engine.recordingIsEmpty(url)` tells the UI to delete it.
- **Stereo split recording (2026-10-12).** `startRecording(id, to: wavURL, layout: .stereoSplit)` creates two pjsua recorders from one base name (`RecordingFiles.planned(for:layout:)`): `<base>-local.wav` gets only the microphone (conference port 0), `<base>-remote.wav` the call's port and every other leg of its conference; `wavURL` itself is not created. Both are 16 kHz 16-bit mono, created in the same engine turn (the bridge adds them on the same frame) and destroyed together by `cpjsua_recorders_destroy_wait` (all removals queued in one call, so they leave on the same frame; then it waits for every header): the files have the same length (0 bytes difference in the self-test; at most one 20 ms frame = 640 bytes is allowed). Both are wired only while the recorded leg's media is up, as in mono. **Mute (deviation from "disconnect the mic"):** pjmedia's bridge sends no frame at all to a port without transmitters (`write_port`: NULL frame, the WAV writer skips it), so disconnecting mic -> local while muted would stop that file and the pair would drift apart. The mic stays connected and the local recorder's tx level is set to 0 (`pjsua_conf_adjust_tx_level`, applied by `reconcileMedia`, `Recording.localAudible`), which writes silence; unmute sets it back to 1. `.mono` is unchanged (`RecordingFiles.mixed`, mic disconnected while muted). Every conference rule below applies to the pair as a unit (one `Recording` with `ports`); `stopRecording` returns the `RecordingFiles`. `recordingFiles(of:)` gives the files of the recording that covers a call (own or conference's) while it runs, and the finished set of a call whose recording ended with the call (`.callEnded` with `isRecording`), kept for the last 32 such calls; nil after an explicit `stopRecording`. `RecordingConverter.convert(files:to:)`: `.mono` -> `convert(wav:to:)`; `.stereoSplit` -> AVAudioFile reads both WAVs in 4096-frame chunks (sizes repaired first, the shorter padded with silence, both without samples -> `.empty`), AVAudioConverter resamples to 44.1 kHz (48 kHz sources stay at 48 kHz), AAC stereo 128 kbit/s (left = local, right = remote); same partial-file + no-overwrite move as mono; the WAVs are left for the caller to delete, as with `convert(wav:to:)`.
- **A conference recording belongs to the conference.** `startRecording` on a leg whose conference is already recorded -> `.invalidArgument("the conference of call X is already being recorded (by Y)")`; `stopRecording` on any leg of a conference stops the conference's recording (the owner is resolved through membership) and clears `isRecording` on the owner. When the owning leg is split off or ends while other legs of its conference remain, `rehomeRecordings()` (start of every `reconcileMedia`, and before conferences are dissolved in `split` and after a call ended) moves the recorder - same pjsua recorder, same file, which keeps growing - to the first remaining leg without its own recording: `.callChanged` for the new owner (`isRecording` true) and, if the old owner is still live, for it (false); an ended old owner's `.callEnded` carries `isRecording == false`. A conference whose legs were all recorded before the merge (auto-record) keeps one recording per leg, each with the whole mix; such a recording is not moved onto a leg that has its own. `isRecording` is true only on the owning leg; the UI shows REC for the conference when any leg has it.
- **PJSIP 2.17: the WAV header is finished asynchronously.** Conference ports are removed on the next audio frame, and the WAV writer writes the RIFF/data sizes in its `on_destroy`, which runs when the bridge drops its group-lock reference. `cpjsua_recorder_destroy_wait` adds a group-lock destroy handler to the recorder port (handlers run FIFO, so it runs after the writer's own), calls `pjsua_recorder_destroy` and waits up to 150 ms (typically one 20 ms frame) on the engine queue. If the bridge does not run in time (no sound clock), the engine patches the RIFF and data sizes from the file length itself (`WAVFile.repair`) and logs it, so the returned file is always valid; PJSIP rewrites the header (and appends what it still buffered) when it processes the removal later, at the latest in `pjsua_destroy`. Not exercised by tests (the null sound device always runs); the repair function is.
- **Recording at call end (deviation).** PJSIP deinitialises the call's media (queues the removal of its conference port) *before* `on_call_state(DISCONNECTED)`, so the recorder cannot be stopped before the port goes; it is stopped by the follow-up on the actor right after (at most the last frame is lost). To keep "`.callEnded` with `isRecording` = a finished file", the bridge holds back the `.callEnded` of a recorded call (`deferredEnds`, keyed by serial) and releases it after the WAV is finalised (typically ~20 ms later) or after the recording moved to another leg (then with `isRecording == false`). The record is still removed in the callback, so no `.callChanged` can follow. `stop()` finalises all recordings before `pjsua_call_hangup_all` and releases the held-back events after `pjsua_destroy`.
- **Call-Info answer-after (security).** In `on_incoming_call` every `Call-Info` header of the INVITE is printed with `pjsip_hdr_print_on` (PJSIP has no dedicated parser for it) and scanned for an `answer-after=N` parameter: after any `;` (`<sip:pbx>;answer-after=0`, the bare `;answer-after=5`) or at the start of the value, case-insensitive, blanks around `;`/`=` and a quoted number accepted, capped at 86400; first match wins. It is honoured only when the INVITE comes from the account's own server, because pjsua routes INVITEs that match no account to the default account and anyone who reaches the SIP port could otherwise make us answer with the microphone open. Trusted sources per pjsua account: the source of the last REGISTER 2xx (`cbparam->rdata->pkt_info.src_name/src_port` and transport, stored in `on_reg_state2`, cleared when the account is not registered, removed, or gets another registrar/proxy/transport), and the configured outbound proxy when it is an IP literal (a host-name proxy is covered by its REGISTER answer, since REGISTER goes through it). Match: same transport and IP address; over UDP also the same port (TCP/TLS servers may open a new connection from another port). Otherwise `answerAfter` stays nil and `.log` says "call N: ignored answer-after from untrusted source ADDR:PORT/transport". An unregistered account therefore never auto-answers by header. Tests cover both paths: a raw-UDP INVITE (untrusted, nil + warning) and a registrar stub that answers REGISTER with 200 and then sends the INVITE from the same socket (trusted, 5; another port on the same host is not trusted).
- **Presence (watching).** `subscribePresence(uri:)` normalises the URI (trim, drop `<...>`, lower-case scheme, add `sip:`; `tel:`, other schemes and empty input -> `.invalidArgument`, then `pjsua_verify_sip_url`), keys the subscription by it (second subscribe = no-op) and calls `pjsua_buddy_add` with `subscribe = PJ_TRUE`, no fixed account (pjsua picks it per request with `pjsua_acc_find_for_outgoing`: domain match, else the default) and a token (a fresh serial) as user data. Events are matched by that token, never by the URI (pjsua buddy ids are reused, URIs may be long); the watch entry exists before `pjsua_buddy_add` because pjsua may call `on_buddy_state` from inside it. `.buddyPresence` carries the URI exactly as first passed (the UI normalises its own key) and the PIDF/RPID note as received (trimmed; nil when empty or after a terminated subscription), and is emitted only when the status or the note changed. pjsua's `pjsua_buddy_add` asserts (aborts a debug build) beyond `PJSUA_MAX_BUDDIES` (256), so the engine throws `.invalidArgument("too many presence subscriptions (limit 256)")` first. `unsubscribePresence` calls `pjsua_buddy_del` first (it takes the dialog lock and clears the subscription's module data, so no callback runs after it) and forgets the URI only on success; unknown URIs are a no-op. A failed SUBSCRIBE is retried by pjsua only after 300 s, so the engine calls `pjsua_buddy_update_pres` (no-op for active subscriptions) for the buddies an account serves after `updateAccount` and when that account becomes registered. `stop()` clears the list without events; after a restart the caller subscribes again. `on_pager` stays unset.
- **Presence mapping.** Subscription TERMINATED or basic status offline/unknown -> `.offline`. Online: a note of "Ringing", "Early" or "Alerting" (case-insensitive, trimmed) -> `.ringing`, whatever the activity (Asterisk/FreePBX report a ringing extension as basic open + `<note>Ringing</note>` + `<rpid:on-the-phone/>`). Otherwise RPID activity busy or on-the-phone -> `.dnd`, away -> `.away`; with no known activity a note of "On the phone", "Busy" or "Do Not Disturb" -> `.dnd`; else `.available` (Asterisk's NotInUse note "Ready" included). pjsua (pjrpid) delivers a `<note>` placed directly under `<presence>` also when a `<dm:person>` element is present (checked by the stub test with and without one). pjrpid only recognises `busy` and `away` and reports Asterisk/FreePBX's `<rpid:on-the-phone/>` as unknown and does not expose the element, so `on_buddy_evsub_state` (which pjsua calls right before `on_buddy_state` for the same NOTIFY) scans the received NOTIFY body for `on-the-phone` and keeps a per-buddy flag; a NOTIFY without it clears the flag. The first event is usually `.offline` (subscription SENT, no NOTIFY yet). `on_buddy_state` fires for every NOTIFY (PJSIP's evsub calls `on_evsub_state` on each one). `.ringing` is never one of our own statuses; `publishPresence(.ringing)` would publish online/busy + "Ringing" (what Asterisk sends). `PresenceStatus` decodes unknown raw values as `.offline`, so settings written by a newer version still load. A test stub (accepts SUBSCRIBE, sends Asterisk-style PIDF NOTIFYs) checks activity-only on-the-phone, Ringing (with and without on-the-phone) -> `.ringing`, InUse -> `.dnd`, Ready -> `.available`, away and closed, and the note in each event.
- **Dialog-info (RFC 4235) is not used (follow-up).** The pjsua buddy subscribes to `presence` only, so `application/dialog-info+xml` never reaches it. PJSIP 2.16+ has a client for the `dialog` event package in pjsua (`pjsua_buddy_config.subscribe_dlg_event`, `pjsua_buddy_subscribe_dlg_event`, `on_buddy_dlg_event_state`, `pjsua_buddy_get_dlg_event_info` with `dialog_info_state` / dialog `state` such as `early` / `confirmed`), but one buddy holds either the presence or the dialog subscription, never both. BLF over dialog-info (needed for PBXs that do not put "Ringing" in PIDF, and to learn the caller for directed pickup) would need a second pjsua buddy per watched URI (counted against `PJSUA_MAX_BUDDIES`) or a per-key choice of package, with `early` -> `.ringing`, `confirmed` -> `.dnd`, `terminated` / no dialogs -> the presence status.
- **Presence (publishing).** `AccountMapping` sets `publish_enabled` from `AccountConfig.publishPresence` and `publish_opt.queue_request = PJ_TRUE`. pjsua accounts start with `online_status = 0` and send the first PUBLISH only after REGISTER succeeds, so `addAccount` sets "available" right away for publishing accounts. `publishPresence` -> `pjsua_acc_set_online_status2` with a PERSON RPID element: available = online/unknown, away = online/away, dnd = online/busy + note "Do Not Disturb", offline = closed. The last status is kept per account and re-applied by `updateAccount` (switching publishing off makes pjsua un-PUBLISH and reset the status to offline). Accounts without `publishPresence` -> `.invalidArgument`. PUBLISH failures (e.g. 489/501 from a server without presence) are only logged by pjsua; there is no event for them.
- **Audio device changes.** `handleAudioDevicesChanged` refreshes PJSIP's list and re-resolves the remembered names, but calls `pjsua_set_snd_dev2` only when the resolved capture or playback index differs from the applied one (a virtual device from Zoom/Teams appearing must not reopen the sound device mid-call). The ringtone is restarted only when its separate device resolves differently. The index can still change for the same physical device when a device listed before it disappears; then the device is reopened, because pjsua opens later streams by index.
- **Tests.** Loopback (one engine calling itself twice, four legs): merge with a held leg, per-leg mute/hold in the conference, applied bridge connections, conference recording (call + partner + mic), WAV header, split of the recording leg (recording moves), stop through another leg, refusal of a second conference recording, the recording leg ending (recording moves, file keeps growing, `.callEnded` flags), the last leg ending with a final WAV when `.callEnded` arrives; a stereo split recording of a conference leg (remote file hears call + partner, local file the mic only) that moves on split; `loopbackStereoSplitRecording` (a 600 Hz WAV played into the answering leg with a test-only pjsua player, 3 s with the middle second muted: local level 0 while muted, both files final and within 640 bytes, remote RMS > 300, local < 50 with null audio, stereo M4A; then the call ends while recording: `.callEnded` with both headers final, `recordingFiles(of:)` still names them); `stop()` while recording; argument checks without calls; presence bookkeeping, normalisation and the 256 limit (no network); Asterisk-style NOTIFYs via a presence stub (incl. ## Implementation notes (milestone 4)
- **"Unsuitable transport selected" on every authorised INVITE (fixed).** Symptom on the owner's account: each INVITE and re-INVITE logged `Temporary failure in sending Request msg INVITE/cseq=N (tdta...), will try next server: Unsuitable transport selected (PJSIP_ETPNOTSUITABLE)` and the next attempt went out. Cause: RFC 3261 18.1.1 in PJSIP (`stateless_send_resolver_callback`, sip_util.c): a request of 1300 bytes or more (`PJSIP_UDP_SIZE_THRESHOLD`) to a UDP destination gets TCP copies of the resolved addresses put in front ("exceeds UDP size threshold (1300), sending with TCP", level 5). Our accounts are bound to their transport (`transport_id`, i.e. a `PJSIP_TPSELECTOR_TRANSPORT` selector on the UDP transport), so `pjsip_tpmgr_acquire_transport2` refuses the TCP entry (sip_transport.c:2540, selector type UDP != TCP), the transaction logs the temporary failure and sends the UDP entry. It is not a resolver or STUN problem: it happens with an IP literal too and was reproduced with an IP target. An INVITE crosses 1300 bytes once it carries a digest `Authorization` header: the first INVITE is answered 401, the authorised retry (cseq N+1) and every re-INVITE (pre-authorised from the cache, `PJSIP_AUTH_AUTO_SEND_NEXT`) are 1370-1400 bytes even on localhost; public addresses from STUN, SRTP crypto lines and longer host names add more. Unregistered localhost calls to pjsua are about 1090 bytes, which is why the first self-test never showed it. Fix: `Engine.start` sets `pjsip_cfg()->endpt.disable_tcp_switch = PJ_TRUE` (Engine.swift, `initPJSUA`). With accounts pinned to a transport the switch could never succeed, so nothing else changes; the request still goes over UDP (it may be IP-fragmented, as before). Proof: self-test step "registered account" (below) failed with exactly the owner's line before the fix; at `SELFTEST_LOG_LEVEL=5` the "exceeds UDP size threshold" and ETPNOTSUITABLE lines are gone after it.
- **Ruled out / remaining.** (1) Resolver: `pj_getaddrinfo` already drops duplicates across socket types; an A-only host name with a port (`127.0.0.1.nip.io:5080`) resolves to one address and sends at once. A host name that also has an AAAA record (`localhost` -> `[::1]`, `127.0.0.1`) still logs the same line once per request: the IPv6 entry comes first and the IPv4 UDP transport the account is bound to does not fit. Harmless (the IPv4 entry follows immediately); the engine creates IPv4 transports only, and pjsua's `ipv6_sip_use` preference (IPv4 first) is ignored when `transport_id` is set. Revisit if an IPv6 transport is added. (2) `transport_id` itself is not the trigger: the selector only made the TCP copy fail; unbinding UDP accounts would have sent large requests over TCP to servers that may not listen on TCP (connection timeouts). (3) STUN / `allow_contact_rewrite` / `allow_via_rewrite`: "IP address change detected" only rewrites Contact and the Via sent-by and re-REGISTERs (`acc_check_nat_addr`, pjsua_acc.c); the account keeps the same transport object. Checked with STUN on (`stun.l.google.com:19302`, mapped public address in Contact/SDP): INVITE 1466 and re-INVITE 1523 bytes go straight out over UDP.
- **Selftest additions** (`SelfTestCalls.swift`, `SIPStub.swift`; the script starts both pjsua phones with `--id sip:phone1@...` / `sip:phone2@...` and telnet CLIs 5088 / 5089). Attended transfer: call #1, hold, call #2, `attendedTransfer(call1, replacing: call2)`; final NOTIFY 2xx, both legs end (the second with pjsua #2's BYE after it accepted the INVITE with Replaces, no extra pjsua flag needed), the phones are in a confirmed call with each other. pjsua has no option to drop telephone-event from its SDP, so DTMF over INFO and the registered account use `SIPStub`, a UDP server in macrosip-cli that challenges REGISTER and INVITE with a res_pjsip-style digest 401 (qop=auth, long nonce, opaque), accepts any `Authorization`, answers PCMU-only SDP without telephone-event and records INFO bodies and INVITE sizes. The script takes `SELFTEST_LOG=<file>` (full output) and `SELFTEST_LOG_LEVEL=<n>`.
- **Hold/resume while a re-INVITE is in flight.** PJSIP refuses a second re-INVITE while an INVITE transaction (ours or the remote's) or a media change is pending (`pjsip_inv_reinvite` -> `PJ_EINVALIDOP`, logged by pjsua as "Unable to create re-INVITE"; `PJSIP_EBUSY` / `PJSIP_ESESSIONSTATE` are treated alike). `setHold` on a confirmed call no longer throws then: like a REGISTER in flight, the request is remembered per call in `Engine.pendingHolds` (latest request wins, a `.log` level 4 says "hold/resume waits for the re-INVITE in progress") and `isOnHold` shows it at once. It is dropped when the call ends, when `merge` resumes the leg, on `stop()`, or after 40 s / a non-busy error (logged; `localHold` then follows the real media state). `.callChanged` follows the media state, so the last one reflects the final state. ## Implementation notes (audio)
Code: `Engine+Quality.swift` (quality, volumes, codec options), `CallQualityModel.swift` (pure MOS model), `TonePlayer.swift` (gain port), C helpers in `Sources/CPJSUA` (`cpjsua_gain_port_*`, `cpjsua_opus_set_options` / `cpjsua_opus_get_options`, `cpjsua_rtp_stat` gained the latest jitter and RTT). Public types in `EngineTypes.swift`: `QualityLevel`, `CallQuality`, `CodecOptions` (decodes missing keys as the defaults). All additions are additive; `start(network:codecPriorities:)` still compiles (`codecOptions` defaults to `CodecOptions()`).

- **Call quality** (`quality(of:)`). Reads `pjsua_call_get_stream_stat` (RTCP part) of the call's audio stream. The engine keeps the previous sample per call; the reported loss is `lost / (received + lost)` over the window since the previous `quality(of:)` (the UI polls every 2 s, so the window is about 2 s) and the jitter is the latest RFC 3550 interarrival jitter. The first call for a call, or a call whose counters went back (a re-INVITE recreated the stream), reports the all-time loss and the mean jitter. A window without any packet received or lost (remote stopped sending, network gone, held) has no loss figure and is reported as poor (MOS 1, loss 100 %); the UI hides quality for held calls. When pjmedia lowers `rxLost` after a late (reordered) packet, the window's loss is clamped at 0 instead of falling back to all-time values; only a lower packet count (new stream) does that. RTT is the latest RTCP value (`rtcp.rtt.last`), 0 until the first receiver report with LSR (RTCP runs every ~5 s). Samples of ended calls are dropped. MOS (`CallQualityModel`, simplified ITU-T G.107): R from the codec's best case (Opus and G.722 MOS 4.4, G.711 4.1, others 4.1; inverted with the G.107 MOS(R) curve), minus Id = 0.024 d + 0.11 (d - 177.3) H(d - 177.3) for the one-way delay d = RTT/2 + 2 x jitter + 20 ms, minus Ie,eff = 95 Ppl / (Ppl + Bpl) for random loss (Bpl 25.1 for G.711 with PLC per G.113 Appendix I; 20 for Opus and G.722, a conservative choice since no standard value exists; 10 otherwise); MOS clamped to 1.0...4.5; good >= 3.8, fair >= 3.0, else poor. Reference table (tested): 0 % / 10 ms -> 4.38 good, 5 % / 40 ms -> 3.66 fair, 15 % / 100 ms -> 2.16 poor (Opus); G.711 4.07 / 3.30 / 1.90. The delay term needs RTT; until RTCP has one, delay counts only jitter and packetisation.
- **Per-call volume** (`setCallVolume`, `setDefaultCallVolume`). Connection levels, not port levels: `speaker` is the level of the call -> sound device connection (slot 0), `microphone` the level of the sound device -> call connection. `reconcileMedia` makes these connections with `pjsua_conf_connect2` (`pjsua_conf_connect_param.level`) and, when the level of a requested connection changes, queues `pjmedia_conf_adjust_conn_level` (shim `cpjsua_conf_adjust_conn_level`, through `pjsua_get_var()->mconf`; pjsua has no wrapper) after any pending connect, so it reaches the connection whichever request PJSIP applies (2.17 queues connect, disconnect and level changes in order). Every other connection (recorders, conference partners) stays at 1: the speaker volume does not change a recording or what the other legs of a conference hear, and the microphone volume does not change the recording either. Levels are 0...2, clamped (NaN = 1), stored by pjmedia in steps of 1/128. Remembered per `CallID` (`requestedLevels` per connection) and used every time the connection is made again (hold/resume, re-INVITE, merge, unmute; mute removes the microphone connection as before). A call gets the default when the engine first wires it; changing the default does not touch calls that already have media. Volumes of ended calls are dropped. (Before review: `adjust_rx/tx_level` of the call's port, which also scaled recordings and conference partners.)
- **Ringtone volume** (`setRingtoneVolume`). 0...1, remembered across ringtone start/stop and engine restarts, settable before `start`. The ringtone source (tone generator or WAV) is wrapped in a small pjmedia port in the shim (`cpjsua_gain_port_create`) that scales the 16-bit samples by an atomically updated gain, so the same mechanism works for the conference-bridge path and for a separate ringtone device (`pjmedia_snd_port`, no bridge, where `adjust_rx_level` would not exist). The gain port owns the source port and the pool: it is destroyed with `pjmedia_port_destroy` after the bridge removal / sound port close, and releases both in its `on_destroy` once the bridge dropped its reference (PJSIP 2.17 removes ports on the next frame; the old code released the pool immediately). Ringback is not scaled.
- **Codec options** (`CodecOptions`, `setCodecOptions`, `start(... codecOptions:)`). Applied with `pjsua_codec_get_param("opus")` + `pjmedia_codec_opus_get_config` + `pjmedia_codec_opus_set_default_param` (PJSIP 2.17 has no `pjmedia_codec_opus_set_config`; `pjmedia_codec_opus_config` has `packet_loss`, `complexity` and `cbr`, no `dtx` field). FEC on: `packet_loss` = 10 (config and `setting.packet_loss`; opus.c reads the config when a codec opens and `setting.packet_loss` in `codec_modify`); off: 0. libopus only adds LBRR redundancy when the expected loss is above 0, and opus.c enables in-band FEC in our encoder only when the remote's SDP has `useinbandfec=1` (RFC 7587: a receiver preference). PLC (`setting.plc`) stays on in both cases, so our SDP always says `useinbandfec=1` (we decode the remote's FEC). DTX: `setting.vad` = 1, which opus.c turns into `OPUS_SET_DTX` (Opus-internal; PJSIP's silence detector is not involved) and `usedtx=1` in our SDP. PJSIP's own VAD stays off globally (`no_vad = 1`): pjsua then zeroes `setting.vad` of every stream, and opus.c re-enables DTX from the remote's `usedtx=1` when the codec opens, so our encoder uses DTX when the far end asks for it (RFC 7587 semantics: `usedtx` is the receiver's preference), and with DTX on we ask the far end for it. Observed in a loopback call with DTX on at log level 5: "Initialize Opus encoder ... vad: 1, plc: 1, pkt loss: 10", the stream's 600 ms VAD suspension, then "VAD re-enabled"; with both off: "vad: 0 ... pkt loss: 0". **Existing calls keep their encoder settings**: the options are the codec's defaults for streams created afterwards (new calls; a re-INVITE that recreates the stream, e.g. after a codec change, picks them up too). The static Opus config survives `stop`/`start` inside one process, but `start` applies its `codecOptions` every time.
- **Tests.** `EngineAudioTests.swift`: MOS table (Opus, G.722, G.711; good/fair/poor rows and a long-delay row), bounds/monotonicity/inverse, window arithmetic (first call, delta, no packets = poor, lower `rxLost` clamped, counter reset), clamping, `CodecOptions` decoding of `{}`; loopback `loopbackCallVolumeAndQuality` (default volume on both legs; a 600 Hz WAV played into the answering leg: the level the bridge sends to the sound device is > 40 at unity, exactly 0 for 1 s with speaker 0 on the calling leg, louder with speaker 2; a 1 s mono recording of the calling leg has the same RMS at speaker 1 and speaker 0 (within 30 %); microphone 0 on the answering leg is the level of its microphone connection, kept across mute/unmute; levels re-applied after hold/resume; quality of the clean call `good` with 0 % loss, also for a 1 s window; state dropped after hang-up); `ringtoneVolume` (volume set before start, live changes measured on the ringtone's conference port: 0 -> level 0, 1 -> audible; clamping; remembered for the next ringtone and across `setRingtoneFile`); `codecOptionsApplied` (defaults with the old `start` signature, live change, `start` with options, read back via `pjmedia_codec_opus_get_config` and the codec manager's default parameters and fmtp, a call with DTX negotiates Opus); `failedReopenKeepsTheClockRunning`; `deviceEventsAreDebounced` (three events 50 ms apart give one `.audioDevicesChanged`). Self-test step "quality": all-time and window quality of the first call to pjsua (window across the stereo recording), must be `good` (typically MOS 4.39, 0 % loss).

## Call options
Code: `Engine+CallOptions.swift` (`setCallOptions`, call-waiting tone, in-band DTMF), the busy check in `pjOnIncomingCall` (`EngineBridge.swift`), `reconcileTones` (`Engine+Audio.swift`), `sendDTMF` (`Engine+Calls.swift`), `TonePlayer` (any source, any sink slot), C helpers `cpjsua_call_send_dtmf2`, `cpjsua_tone_sequence_create`, `cpjsua_dtmf_generator_create` / `_play`, `cpjsua_tonegen_busy`, `cpjsua_conf_listener_count`. Additive: `start(network:codecPriorities:codecOptions:)` still exists (default call options), so `SIPEngine` keeps compiling.

**Scope: engine-wide, not per account.** One `CallOptions` for the engine, set by `start(... callOptions:)` (replaces what `setCallOptions` set before `start`) and changed live by `setCallOptions`. The bridge keeps a copy under its lock, because Do Not Disturb and single-call mode are decided inside `on_incoming_call`. `doNotDisturb` is looked at when an INVITE arrives, `incomingWhileOnCall` when an INVITE arrives (busy) and on every call state/media change (tones); `dtmfMethod` on every `sendDTMF`, so a change applies to the next digits of a call already in progress (there is no per-call or per-account DTMF setting; the UI stores the options in the settings, not in `AccountConfig`).

**Do Not Disturb (`doNotDisturb`).** First check in `on_incoming_call` after the deny rules (before the 4-call limit and single-call mode): every incoming INVITE is answered **486 Busy Here** at once, before the automatic 180, so nothing rings (no ringtone, no call-waiting tone) and the caller never sees ringing. 486 rather than 480 Temporarily Unavailable: it is what the app sent when it rejected calls in DND itself before the engine flag existed, what busy mode sends, and PBXs treat it as "busy" (voicemail on busy, call-forward busy) instead of "not reachable". Same path and events as single-call mode (`rejectBusy` in `EngineBridge.swift`): the UI gets no `.incomingCall`, only `.callEnded(... .disconnected(code: 486, reason: "Busy Here"))` and `.log(level: 3, "engine: call N from <number> rejected with 486 Busy Here (do not disturb)")`. Live through `setCallOptions`; calls in progress and outgoing calls are not affected. The app's own reject on `.incomingCall` during DND can stay as a fallback (it then never fires while the engine flag is set).

**`.busy` (single-call mode).** In `on_incoming_call`, after the 4-call limit check: if another call is in progress the new call is answered 486 Busy Here at once (same path as "too many calls": record created unannounced, `cpjsua_call_answer(486)`, `pjsua_call_hangup(486)` as fallback). "In progress" (`EngineBridge.hasCallInProgress`) = another call whose last INVITE state is CONFIRMED (connected or held, local or remote), CONNECTING (answered, waiting for the ACK), or an outgoing call in CALLING/EARLY (being set up, ringing). The state comes from `CallRecord.inviteState`, stored by every `updateCall`, so the callback does not lock other calls. Another incoming call that is still ringing does not count (two calls ringing at once both ring). The UI sees no `.incomingCall`, only `.callEnded(... .disconnected(code: 486, reason: "Busy Here"))` (direction incoming, duration 0) and `.log(level: 3, "engine: call N from <number> rejected with 486 Busy Here (single-call mode, another call in progress)")`; the call-log note is the UI's.

**`.callWaiting`.** `reconcileTones` computes "talking" = a CONFIRMED call that is not on local hold (media status not local hold, `CallRecord.localHold` false). With incoming calls ringing (not silenced) and talking, the ringtone is stopped and the call-waiting tone plays instead: a `TonePlayer` on slot 0 (the call output, not the separate ringtone device) whose source is one looping tone generator (`cpjsua_tone_sequence_create`) with two entries, 440 Hz 150 ms on / 100 ms off and 440 Hz 150 ms on / 9600 ms off, amplitude 3277 (-20 dBFS): a double beep at once, then every 10 s (`callWaitingPeriodMs`, tests use 1 s). It stops when no incoming call rings any more, when no call is talking (then the ringtone plays), and on `silenceRingtone()`. It is connected only tone -> slot 0 (sink side of the sound device); calls and recorders take their microphone from slot 0's source side, so the tone never reaches the far end or a recording. With only held calls the normal ringtone rings. `.windowOnly` keeps the plain behaviour: the ringtone (on the ringtone device or the speaker) while a second call rings. `.busy` behaves like `.windowOnly` for a call that still rings (it arrived before the other call was answered).

**DTMF method.** `.automatic`: `cpjsua_call_send_dtmf2(CPJSUA_DTMF_AUTO)` = RFC 2833 (`pjsua_call_send_dtmf`, method RFC2833), on `PJMEDIA_RTP_EREMNORFC2833` SIP INFO (the original behaviour). `.rfc2833`: RFC 2833 only; without telephone-event in the remote SDP `sendDTMF` throws `.unsupported("RFC 2833 DTMF: the remote did not offer telephone-event")`. `.sipINFO`: one INFO (`application/dtmf-relay`, `Signal=`/`Duration=`) per digit, whatever the SDP says. `.inband`: a tone generator (`cpjsua_dtmf_generator_create`, the bridge's format, pjmedia's standard digit map) in its own `TonePlayer` whose sink is the call's conference port; `pjmedia_tonegen_play_digits` queues the digits with 100 ms on / 50 ms off at `PJMEDIA_TONEGEN_VOLUME`. The generator is made on the first in-band digit of a call, reused while the call's port number stays the same (made again after it changed; when the number is the same but the generator's connection to it is gone, as after a stream restart that removed the old port and gave the new one the same slot, it is connected again with `TonePlayer.ensureConnected`) and removed when the call ends (`pruneEndedCallState`) or at `stop()`. Only the call hears the tones: not our speaker, not the call's recording (the recorder takes the call port's received audio and the microphone), not the other legs of a conference. A call without a conference port (no media) throws `.unsupported`. At most 32 digits may wait in one call's queue (RFC 2833 has the same limit in pjmedia's stream); more gives `PJ_ETOOMANY` as `.pjsip`.

**Tests** (`EngineCallOptionsTests.swift`, loopback calls in one engine plus `NetworkStub`, which now records INFO bodies). `busyModeRejectsSecondIncomingCall`: started with `.busy`, the loopback INVITE arrives while our own outgoing call is being set up -> 486 for both legs, no `.incomingCall`, one log line; `.windowOnly`, a call is connected; `.busy` live, a second call -> 486, the first stays connected. `callWaitingToneOnSpeakerOnly`: with a connected and recorded first call, a second call rings: the tone's port transmits to slot 0 and nothing else, the bridge receives level > 10 from it and 0 between the beeps, no ringtone; after the reject the tone stops and the first call's recording has RMS < 50 and no 440 Hz (Goertzel amplitude < 30, measured about 0); `.windowOnly` rings the ringtone instead, a live switch to `.callWaiting` swaps them, holding both legs brings the ringtone back, resuming the tone, `silenceRingtone` silences it. `dtmfMethodsOnLoopback`: `.rfc2833`, `.sipINFO` and `.automatic` arrive as `.dtmfReceived`; `.inband` "1111" -> the generator transmits to the call's port only, the far leg's recording has 697 Hz and 1209 Hz amplitudes > 300 and > 5 x the other DTMF frequencies (measured about 6300 vs 690), and no `.dtmfReceived`. `dtmfMethodsAgainstCalleeWithoutTelephoneEvent` (stub, PCMU without telephone-event): automatic -> INFO `Signal=5`, `.rfc2833` -> `.unsupported`, `.sipINFO` -> INFO `Signal=#`, `.inband` -> no INFO. `doNotDisturbRejectsIncomingCalls`: started with DND, a call gets 486 for both legs, the caller never reaches early/ringing, no ringtone, no `.incomingCall`, one "(do not disturb)" log line; DND off live, a call connects; DND on during it, a new call gets 486 without a call-waiting tone and the first call stays. `inbandDTMFAfterHoldResumeAndLostConnection`: two digits back to back leave one connection; after hold/resume and after the generator's connection was dropped by hand (`disconnectInbandGenerator`, what a stream restart does), "1111" is still heard on the far leg (697/1209 Hz) and the generator has exactly one connection (without the reconnect the second check fails). `callOptionsCoding`: `{}` and unknown values decode as the defaults, round trip, the tone sequence (2 x 150 ms at 3277, 10 s period). Self-test (`SelfTestCallOptions.swift`): single-call mode (in a call with pjsua #2, pjsua #1 calls us: 486 at once, no `.incomingCall`, log line, pjsua #1 idle, our call still connected), Do Not Disturb (no call; pjsua #1 calls us: 486 at once, no `.incomingCall`, log line, pjsua #1 idle) and the DTMF methods against `SIPStub` (RFC 2833 only -> unsupported, SIP INFO only -> one INFO `Signal=7`, in-band -> no INFO).

## Voice processing
Apple's `kAudioUnitSubType_VoiceProcessingIO` (VPIO: echo cancellation, noise suppression and gain control, as FaceTime) versus PJSIP's WebRTC echo canceller on HALOutput. Sources: `pjmedia/src/pjmedia-audiodev/coreaudio_dev.m` (Objective-C in 2.17), `pjmedia/src/pjmedia/sound_port.c`, `pjsip/src/pjsua-lib/pjsua_aud.c`.

**How PJSIP 2.17 chooses.** No `config_site.h` flag or rebuild is involved. `ca_factory_init` finds the VPIO component on macOS too and `ca_factory_refresh` advertises `PJMEDIA_AUD_DEV_CAP_EC` (not `EC_TAIL`) on every CoreAudio device (a device-only probe on the development Mac: `EC=1 EC_TAIL=0` for speakers and microphone). With echo cancellation on, pjsua opens the sound device with `PJMEDIA_AUD_DEV_CAP_EC`, and `pjmedia_snd_port` keeps it (device EC) unless `ec_options` has `PJMEDIA_ECHO_USE_SW_ECHO`; then it strips the flag and runs the WebRTC canceller itself. With device EC, `ca_factory_create_stream` switches the stream to VPIO ("Using VoiceProcessingIO audio unit", level 4; confirmed on a real call) and builds one unit for capture and playback. PJSIP's VPIO path on macOS **does not set `kAudioOutputUnitProperty_CurrentDevice`** (comment: it breaks the later buffer-size query with -10879), so VPIO always runs on the system default input and output; it plays Float32, delivers capture at the bridge clock rate, sets no VPIO properties (AGC, ducking, bypass stay Apple's defaults) and is not used for stereo. `cf->io_comp` is factory-wide (opening the separate ringtone device switches it back to HALOutput; only `get_cap(EC)` of the call stream is affected). `EC_TAIL` is unsupported, so `pjsua_set_ec` on an open VPIO stream returns `PJMEDIA_EAUD_INVCAP`.

**Implemented: VPIO on the default devices, the WebRTC canceller on selected ones.**
- `AudioProcessingPolicy.mode` (pure, tested): echo cancellation off -> `.echoCancellationOff`; else if both the input and the output are the system default -> `.systemVoiceProcessing`; else `.softwareEchoCanceller(input:output:)` with the effective device names (the selected one, or the system default's name for the side that is not selected). "Default" means: no name selected, a selected name that is not present (it falls back to the default anyway), or a selected name that resolves to the same device as the current system default. System defaults come from CoreAudio (`kAudioHardwarePropertyDefaultInput/OutputDevice`, named with `kAudioDevicePropertyDeviceName` as PJSIP does, `SystemAudioDefaults`).
- Device events are debounced (`audioDevicesEventArrived`, 400 ms after the last event): a headset plug-in (one list change and two default changes) resolves the mode once and reopens the device at most once.
- `applySoundDevices` (run by `setAudioDevices`, at start, and on every device-list **and default-device** change: `AudioDeviceWatcher` now also listens to `kAudioHardwarePropertyDefaultInputDevice` / `DefaultOutputDevice`) computes the mode, announces a change with `.log` "engine: audio: VoiceProcessingIO" / "engine: audio: software echo canceller on <in> / <out>" (also once at start), and when the canceller *kind* changes calls `switchEchoCanceller`: `pjsua_set_ec(200, PJMEDIA_ECHO_WEBRTC [| PJMEDIA_ECHO_USE_SW_ECHO])`. pjsua reads `ec_options` only when it opens the sound device, so an open device (call in progress) is closed (`pjsua_set_no_snd_dev`), the options set (config only, no port), and the device opened again at once (`cpjsua_open_snd_devs`, `pjsua_set_snd_dev2` without `NO_IMMEDIATE_OPEN`; the bridge and the calls keep running); an idle device just gets the options and the device ids and opens with them on the next call. If the reopen fails, the bridge must not lose its clock: the system default devices are opened at once (`PJMEDIA_AUD_DEFAULT_CAPTURE_DEV` / `_PLAYBACK_DEV`), and if that fails too, the null sound device (calls keep running, silent; `soundOnNullFallback`, so the next switch opens a real device at once while calls exist). The applied state (`appliedSoftwareEC`, `appliedSoundDevices`) is cleared so the next device event or `setAudioDevices` tries again, a level 1 `.log` "engine: audio error: ..." says what happened (for the UI), and `setAudioDevices` throws. Test `failedReopenKeepsTheClockRunning` (loopback, device indices that do not exist for both attempts, so no real device opens): error logged, state cleared, null fallback, RTP keeps flowing both ways. A device change that keeps the kind (one selected device for another) goes through the old path (`pjsua_set_snd_dev2` with `NO_IMMEDIATE_OPEN`, which reopens an open device itself). With `nullAudio` the mode is computed and announced ("(null audio: not applied)") but nothing is applied.
- `public func audioProcessingMode() -> AudioProcessingMode` (`.systemVoiceProcessing`, `.softwareEchoCanceller(input:output:)`, and `.echoCancellationOff` when echo cancellation is switched off) for the UI.
- Consequence for the user: on the system default devices, calls get Apple's processing (and macOS's Mic Mode menu, other-audio ducking); picking a specific device (headset while the default is the speakers) gets exactly that device with the WebRTC canceller (no system noise suppression). Making the headset the system default instead brings VPIO back.
- Tests: `audioProcessingPolicy` (table: nothing selected, selected = default, absent devices, non-default input or output, default changed to the selected device, an output-only device named as input, unknown default, echo cancellation off); `audioProcessingModeFollowsDeviceSelection` (real CoreAudio, no device is opened because no call runs: default -> VPIO and announced; the default output selected by name stays VPIO; a non-default output, else input, by name -> software canceller applied; on a Mac with one input and one output it selects the output by name and makes the engine treat another name as the default (`overrideDefaultDeviceNames`, test hook) to exercise the same path; back to VPIO; echo cancellation off -> `.echoCancellationOff`).
- **Not covered by automated tests: the mid-call reopen.** It needs a real sound device during a call, which opens the microphone; a test process without microphone permission hangs inside VPIO's `AudioUnitSetProperty` at call start (seen once while trying, before any switching code ran). Owner's check (`--log-level 4`): in a call on the default devices, select headphones in Settings: the log shows "engine: audio: software echo canceller on ...", "sound device reopened", "Using default audio unit", and the call continues on the headphones; select "System default" again: "VoiceProcessingIO" again.

**Not done, possible later.** A `coreaudio_dev.m` patch that sets `kAudioOutputUnitProperty_CurrentDevice` on the VPIO unit per element (input element 1, output element 0) and skips the buffer-size property for VPIO would give Apple's processing on any device: estimated 40-80 lines carried by `scripts/build-pjsip.sh`, medium to high risk (poorly documented, differs between macOS versions and with aggregate/Bluetooth devices), needs testing on several devices. VPIO tuning (AGC, `kAUVoiceIOProperty_OtherAudioDuckingConfiguration` on macOS 14+) would be a small post-open hook. Risks either way: Bluetooth headsets drop to the hands-free profile when their microphone is used; a separate ringtone device (HALOutput) may be ducked by VPIO during a call; VPIO's AGC can pump.

## Network resilience
Goal: a network drop, a Wi-Fi -> Ethernet/LTE switch, an IP change or sleep/wake must not leave the phone unregistered for minutes, and a call survives an IP change. Code: `Engine+Network.swift`, `NetworkPathMonitor.swift`, bridge callbacks `on_ip_change_progress`, `on_transport_state`, `on_call_tsx_state` and the retry part of `on_reg_state2` (`EngineBridge.swift`), C helpers `cpjsua_handle_ip_change`, `cpjsua_acc_prepare_ip_change`, `cpjsua_call_reinvite_ip_change`, `cpjsua_call_cancel_reinvite`, `cpjsua_call_send_options`, `cpjsua_tsx_final`, `cpjsua_accounts_on_transport`, `cpjsua_set_keep_inv_after_tsx_timeout`, `cpjsua_rtp_stat.rtcp_rx_reports`.

**API (additive).** `NetworkState` (`.online`, `.offline`); `EngineEvent.network(NetworkState)`, emitted once after `start` with the first path evaluation and on every change; `RegistrationState.reconnecting(attempt:nextRetryIn:lastError:)`; `CallInfo.isReconnecting`; `Engine.networkState()`, `handleWake()`, `handleSleep()`, `simulateNetworkChange()`; `Engine.connectionLostReason == "connection lost"`. The UI shows `.reconnecting` as "Reconnecting... (attempt N, next in S s)" with `lastError` as detail, `.network(.offline)` as a global "Waiting for network" (going offline does not change registration states; they move to `.reconnecting` when a REGISTER fails), `isReconnecting` as a "Reconnecting..." badge on the call, and a `.callEnded` with `.disconnected(code: 0, reason: "connection lost")` as "Connection lost".

**Ordering.** Path updates go through one `AsyncStream` per `NWPathMonitor` and are applied by one consumer task in order (a Task per update could apply an unsatisfied/satisfied pair at wake reversed and leave the engine offline). Follow-up work from PJSIP callbacks (`EngineBridge.hop`) also runs through one ordered queue (one consumer task per started engine), so for example two final responses of the same call, or a REGISTER result and the end of a network change, are handled in the order PJSIP reported them.

**Path monitoring.** `NWPathMonitor` on its own queue (`macrosip.network`). `.satisfied` = online. A path is reduced to its primary route (`NetworkPath`): the first available interface (the one the system routes through), the source address of the default route (a UDP socket "connected" to 192.0.2.1 and read back with getsockname: the address pjsua's sockets use towards a server on the default route) and the first gateway. Secondary interfaces (bridge100 of Internet Sharing, a split-tunnel utun, a second Wi-Fi) coming and going change nothing; a full-tunnel VPN that takes the default route changes the interface and the address. The first update after `start` and every update while a wake is pending are applied at once; later ones are debounced by 2.5 s (the last one wins). Online -> offline: `.network(.offline)`, calls get `isReconnecting`. Offline -> online: `.network(.online)` and a round; a changed primary route while online: a round. A new local address on the same interface and gateway that produces no path update is not noticed (keep-alives, `allow_contact_rewrite` and the next REGISTER refresh deal with it). If no update arrives within 2 s after start, `.network(.online)` is emitted anyway. A satisfied path without a default route (the 192.0.2.1 lookup fails) keeps the previous address and counts as unchanged (logged). `Engine(monitorNetwork: false)` runs no NWPathMonitor: the network counts as online from `start` (a fixed path is reported at once) and only paths injected by tests change it; the engine tests use it so they do not depend on the host's network.

**Rounds (`requestIPChange` / `performIPChange`).** One round = one `pjsua_handle_ip_change`. Rounds never overlap: a request while a round runs is queued (the latest reason, flags merged) and started when the round completes. A request is "primary" when the interface or the local address changed (and for `simulateNetworkChange`); otherwise (gateway-only change, network back with the same address, wake with the same address) it is postponed while an outgoing call is still unanswered and runs when no outgoing call rings any more (checked every second, at most 90 s): pjsua hangs up an account's unconfirmed outgoing calls with 410 after that account's re-REGISTER (`pjsua_acc_handle_call_on_ip_change`; test `ringingCallOfReRegisteringAccountEndsOnAddressChange`), which is accepted only when the address really changed (such a call cannot complete then anyway). Steps: (1) every confirmed call gets `reinviteWanted = round` (`isReconnecting`). (2) `cpjsua_acc_prepare_ip_change` per account decides whether pjsua re-REGISTERs it: pjsua's `handle_ip_change_on_acc` re-registers an account without a registration session only when its last REGISTER status was 200 or a temporary failure, and would therefore also REGISTER an account the user switched off (last code 200 after the un-REGISTER) and skip a working outgoing-only account's calls. The shim sets that internal status to 200 for accounts that should be registered (not while asleep; `.failed` ones only on wake) and to 0 for the rest, which pjsua then skips ("Permanent registration failure, IP change handling will stop for acc N" in PJSIP's log is this skip). A REGISTER that still arrives for an account that is off is undone. (3) `keep_inv_after_tsx_timeout` is switched on by the engine before pjsua sees it (pjsua then does not schedule its own timer that would switch it off one transaction timeout later, while re-INVITEs may still run) and off again when no round runs and no call waits for its re-INVITE, and after `pjsua_destroy`: a re-INVITE that times out does not end the call inside PJSIP; the engine decides. (4) `pjsua_handle_ip_change`: `shutdown_transport` (all TCP/TLS connections), `restart_listener` only when the engine is bound to all interfaces (a restart rebinds to 0.0.0.0 and recomputes the published address; with `bindAddress` set, as in the tests and the self-test, it would undo the binding), `restart_lis_delay` 100 ms. Account config: `ip_change_cfg.shutdown_tp = true`, `hangup_calls = false`, `reinvite_flags = PJSUA_CALL_REINIT_MEDIA | PJSUA_CALL_UPDATE_CONTACT | PJSUA_CALL_UPDATE_VIA`. pjsua re-REGISTERs (new Contact through `allow_contact_rewrite`) and after the 2xx re-INVITEs that account's confirmed calls. (5) On `PJSUA_IP_CHANGE_OP_COMPLETED` of this round (or after one transaction timeout + 5 s without it, so a late report cannot close the next round) the engine re-INVITEs every call of step 1 that pjsua did not (`PJSUA_IP_CHANGE_OP_ACC_REINVITE_CALLS` reports those), except calls whose account's re-REGISTER is still unanswered (pjsua re-INVITEs them after the answer; two re-INVITEs would reinitialise the media twice). Same flags, local hold kept (no UNHOLD flag, pjsua offers the hold SDP), audio only. Then a queued request runs.

**The engine's re-INVITE.** `reinviteInFlight = round` is set before `pjsua_call_reinvite2` is called (on loopback the answer can arrive before it returns) and put back if the call fails synchronously. A transaction in flight (hold, the remote's re-INVITE, an older round's re-INVITE) is waited for in 250 ms steps for up to one transaction timeout. Retry and busy tasks are kept per call and cancelled when a new round starts.

**Re-INVITE result** (`on_call_tsx_state`, final response of an INVITE of a call that wants a re-INVITE; 401/407 are skipped, pjsua repeats with credentials). The answer is attributed to the round of the engine's in-flight re-INVITE, or to the current round if pjsua reported sending one; otherwise it is unattributed (e.g. a hold re-INVITE sent before the change) and only a 2xx while the call's round is still running counts. An older round's re-INVITE answered with any code (also 408): the current round's re-INVITE is sent. The current round's: 2xx -> `isReconnecting` off ("media re-established after network change (200)"); 481 or 408 -> the far end lost the dialog, the call ends as connection lost (PJSIP itself ends the session on 481; the bridge reports such an end of a call with a re-INVITE pending as `.disconnected(code: 0, reason: "connection lost")`); offline or asleep again -> left for the next round; 491 (both ends re-INVITE at once), 5xx -> up to 4 more tries after the RFC 3261 14.1 delay (dialog caller 2.1-4 s, callee 0-2 s; the loopback tests hit this). A re-INVITE that never settles (a server that answers only 100 Trying) is CANCELled and given up two transaction timeouts after the round wanted it; the media watchdog decides from then on. Hold, mute, recording, conference and volume survive: `REINIT_MEDIA` gives the call a new conference port and `reconcileMedia` wires it again; held calls stay held.

**isReconnecting** (`refreshReconnecting`, after every change and each second): confirmed call and (offline, or a re-INVITE wanted or in flight, or RTP silence). RTP silence = no RTP for more than 3 s with active media, and either a network event (offline/online, route change, wake, round) within the last 30 s or no RTCP report for more than 12 s too. A peer with silence suppression or a voicemail recording (Asterisk `Record()` sends no RTP) keeps sending RTCP and is not shown as reconnecting.

**Media watchdog** (1 s tick, `ContinuousClock`, so wall-clock jumps do not count): per confirmed call the RTP packet count and the number of RTCP reports received (`rtcp.tx.update_cnt`). Clocks pause while the media is not active (local or remote hold), the network is offline or the Mac sleeps; a counter that goes back (new stream after a re-INVITE) restarts them and disarms the watchdog until RTCP arrives on the new stream. Armed only after at least one RTCP report on the stream (a peer without RTCP is never ended by it). No RTP and no RTCP for 60 s while online: an in-dialog OPTIONS probe; 408 or 481 -> the call ends as connection lost (PJSIP ends the dialog on these itself; the bridge maps that end the same way); any other answer (200, 405, 501) -> the call stays and the next probe is one period later. Offline calls are never ended by the engine.

**REGISTER retry with backoff.** pjsua's own retry is off (`reg_retry_interval = 0`, `drop_calls_on_reg_fail = false`). `RegistrationMapping.isTemporary`: 408, 480, 500, 502, 503, 504, no code, or a local failure (status other than PJ_SUCCESS: transport error, DNS failure, `PJSIP_ETPNOTAVAIL`, a refresh that could not be sent) -> temporary; 401/403/404/407/423 and every other 4xx-6xx -> `.failed`, no retry. Also permanent: TLS certificate and TLS configuration errors (the reason contains the text of `PJSIP_TLS_ECERTVERIF`, `ECACERT`, `ECERTFILE`, `EKEYFILE`, `EINVMETHOD`, `ECIPHER`, or "certificate"), and a host name that does not resolve (`PJ_ERESOLVE`, `PJLIB_UTIL_EDNS_NXDOMAIN`) after the network has been online for 10 s (a typo in the server name; right after a change DNS may not work yet, so then it is retried). A temporary failure of an account that should be registered emits `.reconnecting(attempt: n, nextRetryIn: d, lastError:)` with d = 2, 4, 8, 16, 32, then 60 s (`RegistrationBackoff`), and a timer sends the REGISTER again after d. While a retry runs the state stays `.reconnecting` (no `.registering` in between). Success resets the count. A REGISTER that cannot even be sent (without a network DNS and sendto fail inside `pjsua_acc_set_registration`; pjsua reports it through `on_reg_state2` before returning the error) is such a temporary failure too: `addAccount`, `updateAccount` and `setRegistered` do not throw or roll back for it (deviation from milestone 2.1's "addAccount rolls back if the registration cannot start", which still holds for other errors), the account stays and is retried, so the app can start offline. A retry that falls due while offline or asleep is not sent (the network coming back or wake re-registers through a round); during a round it waits for it. `setRegistered(true)`, `updateAccount` and wake start a fresh series; switching off cancels it. TCP/TLS: `on_transport_state` DISCONNECTED/SHUTDOWN of the transport an account's registration uses (pjsua's own registration bookkeeping, read in the callback before pjsua releases it) counts as a temporary failure ("TLS connection to ... disconnected") -> the same backoff; ignored during a round (it closes them on purpose). Keep-alives are unchanged.

**Sleep and wake.** `handleSleep()`: un-REGISTERs (Expires 0) every account that should be registered and is registered or registering, cancels retries and a postponed change; accounts keep their configuration and `wantsRegistration`; calls are left alone. `handleWake()`: clears the backoff, restarts the watchdog clocks, creates a new path monitor for a fresh evaluation (its reports are applied in order without debounce while the wake is pending) and, as soon as a report says online, runs a round re-registering every account that should be registered (also `.failed` ones) and re-INVITEing the calls. Offline at wake: the wake stays pending until the path comes back. No report within 2 s: done anyway if the last known state is online.

**Tests** (all engine tests get their engine from `makeEngine()`, which first stops an engine a failed test left started, so one failure cannot cascade into "Engine is already started"; `EngineNetworkTests.swift`; `NetworkStub` is a UDP registrar/callee whose REGISTER answers switch between 200, 403 and none, which answers INVITE without ever sending RTP (optionally RTCP receiver reports every 0.5 s), can leave an INVITE ringing, answers re-INVITE with a configurable status, nothing, or only 100 Trying (CANCEL then gets 200 and the INVITE 487), and OPTIONS with a configurable status). Registration: `networkEventAfterStart` (with the real monitor and without); `registrationRetriesWithBackoff` (transaction timeout 2 s through a test hook: `.reconnecting(1, 2 s, "408 ...")`, retry 2 s later, `.reconnecting(2, 4 s)`, then `.registered`; exactly these three states); `registrationThatCannotBeSentIsRetried` (registrar 255.255.255.255: sendto fails at once; `addAccount` succeeds, attempts 1 and 2, never `.failed`); `forbiddenRegistrationIsNotRetried`; `sleepUnregistersAndWakeRegistersAgain`. Watchdog: `silentMediaProbedThenEndedAsConnectionLost` (RTCP, then nothing: reconnecting, OPTIONS, 481 -> connection lost); `silentMediaProbeAnsweredKeepsCall`; `rtpSilenceWithRTCPIsNotReconnecting` (RTCP but no RTP: not reconnecting, no probe; a peer without RTCP: no probe, not ended). Pure: classification incl. TLS/DNS, delays, primary route comparison, `makeInfo` (connection lost after re-INVITE or probe), the pjsua account fields. Self-test: `.network(.online)` after start; `simulateNetworkChange()` during the first call to pjsua (callChanged with isReconnecting, the engine's re-INVITE answered 200, RTP both ways afterwards); with the registered stub account (REGISTER at the stub, stays registered). The listener restart path (engine bound to all interfaces) was checked once by hand with a loopback call: all four listeners restarted on their ports, published as the LAN address, call continued.

**Manual checks** (`macrosip-cli` interactive): `net`, `netchange`, `sleep`, `wake`.

**Only a real network can verify:** Wi-Fi <-> Ethernet/LTE/hotspot switches and pulling the cable (NWPathMonitor reports, the primary-route reduction, the debounce, the restarted listener's new published address and the Contact rewrite through a NAT), a PBX that receives the re-INVITE from a new address (Asterisk: `rtp_symmetric`/`force_rport`, `direct_media`), TCP/TLS registrations losing their connection, a TLS certificate failure on a real server, an outbound proxy or STUN in the path, sleep/wake with the app's notifications (whether the un-REGISTER leaves before the Mac sleeps), a long outage (backoff reaching 60 s), and how long a real call takes to recover. Owner's check (`--log-level 4`): during a call switch Wi-Fi off and on (or move from Wi-Fi to a phone hotspot): the log shows "network offline", "network online", "network change (network back), round N: re-REGISTER 1 account(s), re-INVITE 1 call(s)", "listener ... restarted", the REGISTER 200, "re-INVITE after network change sent", "media re-established", and the call continues.

## Network options
Code: `Model/NetworkSettings.swift` (fields, decoding, `isValidRTPRange`, `effectiveRTPRange`, `needsRestart(from:)`), `Engine+NetworkOptions.swift` (`applyNetworkSettings`, nameservers, test hooks), `DNSServers.swift` (parsing, system resolvers), `initPJSUA` in `Engine.swift`, `AccountMapping.rtpPortRange`, C helpers `cpjsua_set_nameservers`, `cpjsua_has_resolver`, `cpjsua_call_local_rtp_port`.

- **RTP port window** (`rtpPortStart`, `rtpPortCount`). Per account: `rtp_cfg.port = start`, `rtp_cfg.port_range = max(1, count - 2)`, `randomize_port = 1`. pjsua picks RTP ports at even offsets in `port...port+range` and RTCP = RTP + 1, so every port used lies in `start...start+count-1`; range 0 would mean "no limit", hence at least 1 (a two-port window uses only the start port). Each call needs one pair, so a window of N ports carries N/2 calls (a loopback call two). Valid: start 1024-65535, count >= 2, last port <= 65535 (`NetworkSettings.isValidRTPRange`, for the UI); the engine clamps anything else (`effectiveRTPRange`: start into 1024...65534, count into what fits, at least 2) rather than failing `start`.
- **rport** (`useRport`). pjsua 2.17 has no per-account `use_rport`; it is the endpoint flag `pjsip_cfg()->endpt.disable_rport`, read whenever a request's Via is built. Global and kept across `pjsua_destroy`, so `start` sets it both ways. Live: the next request (REGISTER refresh, INVITE) follows the new value. `allow_contact_rewrite`/`allow_via_rewrite` stay on; without rport they still use `received`.
- **DNS SRV** (`dnsSRV`, `nameserver`). Off (default): no resolver, host names go through the system (`getaddrinfo`, A/AAAA). On: `pjsua_config.nameserver` gets the servers, so pjsua creates the SIP resolver (`pjsip_endpt_create_resolver`); a registrar, outbound proxy or request URI host without an explicit port and not an IP is then resolved with SRV first (`_sip._udp.`, `_sip._tcp.` or `_sips._tcp.` + host, from the account's transport), then A of the SRV target, falling back to A of the host when there is no SRV record (RFC 3263 section 4.2; PJSIP does not do NAPTR, the transport always comes from the account). Explicit ports skip SRV. `nameserver`: "10.0.0.1", "10.0.0.1:5353", "[2001:db8::1]:53" or a bare IPv6, several separated by commas, semicolons or blanks, at most 4; entries that cannot be read and scoped (link-local) IPv6 addresses are skipped. `pjsua_config` only knows port 53, so when a server has another port `cpjsua_set_nameservers` sets the list again with ports (`pj_dns_resolver_set_ns`) right after `pjsua_init`. Empty or nil: the system resolvers, from SystemConfiguration (`State:/Network/Global/DNS` `ServerAddresses`, what macOS itself uses), else the `nameserver` lines of `/etc/resolv.conf` (what `res_ninit` reads). With system resolvers, a network change (route change, back online, wake) re-reads them and updates the resolver if they differ. SRV on but no server known: a level 2 `.log` line and plain lookups. `start` logs "engine: DNS SRV via 10.0.0.1:53, ...".
- **What applies live** (`applyNetworkSettings(_:) -> NetworkApplyResult`, rule in `NetworkSettings.needsRestart(from:)`). Live: `useRport` (endpoint flag), `keepAliveSeconds` and `useICE` (every account is `pjsua_acc_modify`d with `disable_reg_on_modify`, no re-REGISTER; ICE applies to the next call). Needs a restart (`.needsRestart`; the engine keeps running with the old values, the live parts are applied anyway): the RTP window, `dnsSRV`, `nameserver` (only while `dnsSRV` is on), `localPort`, `stunServer`, `echoCancellation`. The app then does `stop()` + `start(network:)` with the stored settings when the user agrees (Settings › Network "Restart now"). Before `start` it returns `.applied` and changes nothing (`start` takes its own settings). The RTP window could technically follow `pjsua_acc_modify` for new calls, but is kept with DNS as "restart" so the UI rule stays simple.
- **Tests.** `Engine262Tests.swift`: value tests (old JSON decodes with the defaults, round trip, RTP range validation/clamping and the `port_range` mapping, restart rules, nameserver parsing and `resolv.conf`); `rtpPortsStayInConfiguredWindow` (loopback call with window 42000+10: both legs' local RTP ports inside and different; `keepAliveSeconds` change -> `.applied`, window change -> `.needsRestart`; a new start with 43100+4 uses that window); `rportFollowsSetting` (`NetworkStub` records the top Via of each REGISTER: no `rport` when started with `useRport = false`, `;rport` on the next REGISTER after a live switch, the endpoint flag back on after `stop`); `dnsSRVResolvesRegistrar` (an in-process DNS stub, `DNSStub`, answers `_sip._udp.example.test` SRV -> pbx.example.test:<NetworkStub port> and its A record 127.0.0.1; with `nameserver = "127.0.0.1:<port>"` an account on domain `example.test` registers at the stub after an SRV query; without SRV no resolver exists; a nameserver change -> `.needsRestart`).

## Deny incoming calls
Code: `CallOptions.denyIncoming`/`knownNumbers`/`denial(fromURI:privacy:)`/`isAnonymous`/`knownNumberKey` (`EngineTypes.swift`), the first check in `pjOnIncomingCall` and `rejectIncoming` (`EngineBridge.swift`), `cpjsua_rdata_header` (Privacy).

- **Rules.** `.nobody` (default) lets everything ring. `.everyone`: every incoming INVITE gets **603 Decline**. `.notInContacts`: 603 unless the caller's From user part, as `CallOptions.knownNumberKey` (= `Contact.normalize` without a leading "+": digits for numbers, the lower-cased user part for SIP names), is in `knownNumbers`; anonymous callers get 603 too. `.anonymous`: **433 Anonymity Disallowed** (RFC 5079) when the caller is anonymous, everyone else rings.
- **Anonymous** = the From user part is empty (`sip:host`), or "anonymous", "unknown", "restricted", "private", "unavailable" (any case), or the From host is `anonymous.invalid` (RFC 3323), or the INVITE has a `Privacy` header with `id` (RFC 3325), `user` or `header`.
- **Where.** Evaluated inside `on_incoming_call` on the PJSIP thread from the bridge's copy of the options, before Do Not Disturb, the 4-call limit and single-call mode, and before the automatic 180: nothing rings and the decision does not depend on the app being responsive. The app keeps `knownNumbers` in sync with its contacts through `setCallOptions` (`Contact.allNormalizedNumbers`); the engine normalises the set once per `setCallOptions`/`start` (`withNormalizedKnownNumbers`) and also accepts numbers in any spelling `Contact.normalize` understands. `knownNumbers` is not encoded (settings.json never holds the address book); `denyIncoming` is, and unknown values decode as `.nobody`.
- **Events.** As for Do Not Disturb: no `.incomingCall`; `.callEnded(info, duration: 0)` with `info.direction == .incoming` and `.disconnected(code: 603, reason: "Decline")` or `.disconnected(code: 433, reason: "Anonymity Disallowed")`, plus `.log(level: 3, "engine: call N from <number or URI> denied with 603 Decline (caller not in contacts)")` (reasons: "incoming calls denied for everyone", "caller not in contacts", "anonymous caller, not in contacts", "anonymous caller"). The UI writes the call-log note (`denied`).
- **Tests.** Value tests (`anonymousCallers`, `denyRules`, `callOptionsJSON`); `denyIncomingRules` (loopback + `NetworkStub`): everyone -> 603 on both legs, no `.incomingCall`, the log line; not in contacts -> 603 with other numbers known, rings once "LOOP" is known; anonymous -> a named caller rings, an account called "anonymous" gets 433 on both legs, a stub INVITE from `sip:200@...` with `Privacy: id` gets a 433 response (`.callEnded` 433, number "200"), the same with `Privacy: none` rings. Self-test step "deny incoming" (`SelfTest262.swift`): pjsua #1 calls us with everyone and with not-in-contacts -> 603 at once, pjsua idle; with its number known it rings.

## Codecs
Built in (`config_site.h` `PJMEDIA_HAS_G7221_CODEC`/`GSM`/`ILBC`/`SPEEX_CODEC` = 1, no `--disable-*-codec` flags in `build-pjsip.sh`, which fails if configure disables one of them or a codec library is missing; sources are pjproject's own `third_party` gsm, ilbc, speex and g7221, linked as `libgsmcodec.a`, `libilbccodec.a`, `libspeex.a`, `libg7221codec.a`, listed in `Package.swift`). The Speex echo canceller stays off (`--disable-speex-aec`; WebRTC AEC is used). No G.729 (bcg729 stays disabled), no L16, AMR, SILK, Lyra.

- **Ids** (`Engine.optionalCodecs`, the order the UI lists them after G.711): `G7221/16000/1` (G.722.1 / Siren7), `G7221/32000/1` (G.722.1 Annex C / Siren14), `GSM/8000/1`, `iLBC/8000/1`, `speex/8000/1`, `speex/16000/1`, `speex/32000/1`. They are not in `Engine.defaultCodecOrder`, so `start`/`setCodecPriorities([])` leave them at priority 0 (disabled) until the user's codec list names them.
- **G.722.1 bitrates.** pjmedia registers one G.722.1 codec per bitrate (16 kHz: 24 and 32 kbit/s; 32 kHz: 24, 32 and 48 kbit/s) under the same id. `codecs()` lists each id once (`CodecMapping.unique`, highest priority); a priority set by id applies to every bitrate, and the SDP offers each one with its own payload type and `bitrate` fmtp.
- **`codecs()` order.** By priority; equal priorities (the disabled codecs) in `defaultCodecOrder` + `optionalCodecs` order, then anything else by name (`CodecMapping.displayOrder`).
- **Tests.** `addedCodecsListedAndGSMNegotiates`: every id is listed once, no G.729; with only `GSM/8000/1` a loopback call negotiates `GSM/8000` on both legs and carries RTP; `setCodecPriorities([])` puts the default four first and the seven new ids after them at 0. `codecDisplayOrder` (value test). Self-test step "codecs" (`SelfTest262.swift`): all seven ids exist; the engine with only GSM calls pjsua #1 (all codecs enabled, an independent implementation): the call negotiates `GSM/8000`, RTP both ways; the default order is restored.

## Hold music
Code: `Engine+HoldMusic.swift` (`setHoldMusic`, `reconcileHoldMusic`, `HoldMelody`), `Recording/AudioFileToWAV.swift`, `TonePlayer`, C helpers `cpjsua_tone_sequence_create`, `cpjsua_wav_loop_create`. Setting: `AppSettings.audio.holdMusic` (`HoldMusic`, default `.builtIn`; unknown JSON decodes as the default).

- **What the far end hears on local hold.** `setHold(id, true)` still sends the re-INVITE with `sendonly` (pjsua's `pjsua_call_set_hold2`). The direction is ours: the stream keeps encoding and sending what the call's conference port receives (pjsua gives a held call's audio stream `PJMEDIA_DIR_ENCODING`), so a source connected to that port is heard at the far end. Without a source the port has no transmitter and the far end gets silence, as before (`HoldMusic.off`).
- **Player per held call.** `reconcileHoldMusic` runs at the end of every `reconcileMedia` (media state, hold, conference, recording changes). For every confirmed call whose media status is local hold (the re-INVITE was answered) it keeps one looping `TonePlayer` connected to the call's conference port only: not to slot 0 (nothing in the speaker), not to recorders (a held call is not recorded anyway, and the player has exactly one listener). Players of calls that resumed, ended or whose port moved are destroyed; a port recreated under the same slot number is connected again (`ensureConnected`). A call is not touched while its hold re-INVITE is still in flight (the far end still hears the microphone then).
- **Sources.** `.builtIn`: `HoldMelody`, a sixteen-note two-voice arpeggio (C, F, G and C major, 320 ms notes, 40 ms gaps, a 1.6 s rest, about 7.4 s per loop, each voice at about -16 dBFS) in one looping tone generator (`cpjsua_tone_sequence_create`; the melody fits the generator's 32-entry queue). `.file(url)`: a WAV whose `fmt` chunk says 16-bit PCM with one or two channels is played as it is by `cpjsua_wav_loop_create` (any sample rate; the bridge resamples). Anything else AVFoundation reads (M4A, MP3, AIFF, CAF, float or 24-bit WAVs) is converted once by `AudioFileToWAV.convert` (channels averaged to mono, resampled to 16 kHz, 16-bit PCM) into `NSTemporaryDirectory()/MacroSIP-hold-music-<uuid>.wav`, off the engine queue (`setHoldMusic` is `async`; a later call that overtakes the conversion wins and the stale file is deleted). The temporary file is replaced on the next `setHoldMusic` and kept across `stop`/`start`. A file that cannot be read throws `AudioFileToWAV.ConversionError` and the previous source stays; a WAV pjmedia refuses when a call is held falls back to the melody with a `.log` line. `.off`: no player.
- **Live changes.** `setHoldMusic` works before `start`, is remembered like the ringtone settings and restarts the players of calls already on hold. The UI applies `audio.holdMusic` at start and whenever it changes; the mock engine needs the same method.
- **Tests.** `holdMusicReachesTheFarEndOnly` (loopback): on hold the player has one listener and none is slot 0, the bridge receives level > 10 from it, the far leg (remote hold from its side, so its port is recorded) records the melody (RMS > 200) while the held leg has no speaker or microphone connection; `.off` records RMS < 50 after the in-flight audio drained; a 600 Hz WAV and an M4A made from it are both heard at 600 Hz (Goertzel amplitude > 300), the M4A through a temporary WAV that `AudioFileToWAV.isPlayableWAV` accepts; a missing MP3 throws and keeps the source; `.builtIn` again deletes the temporary file; resume removes the player, a second hold makes a new one. `audioFileToWAVConvertsAStereoFloatFile` (a 44.1 kHz stereo Float32 WAV is not playable, converts to 16 kHz mono 16-bit, length within 5 %, RMS kept) and `holdMelodyAndSoundsFitTheGenerator` (pure).

## Recording notice tone
Code: `Engine+RecordingNotice.swift` (`setRecordingNotice`, `reconcileRecordingNotices`, `RecordingNoticeTone`), `TonePlayer.setSinks`, C helpers `cpjsua_dtmf_generator_create`, `cpjsua_tone_sequence_play_once`, `cpjsua_conf_listeners`. Settings: `AppSettings.recording.noticeTone` (false) and `noticeToneIntervalSeconds` (15, `RecordingSettings.noticeIntervalRange` 5...60, clamped on init and decode).

- **The beep.** 1400 Hz for 300 ms at about -12 dBFS (the telephony convention for a recorded line), first one second after the recording starts, then every interval. While the recorded call is held nothing is recorded, so no beep is played; the timer keeps running.
- **Who hears it.** One idle tone generator per recording owner (`noticePlayers`), connected to: the recorded call's conference port (the far end), the ports of its conference partners (they are recorded too), slot 0 (the local user) and the recording's files that carry the far end, i.e. the mixed file, or the remote file of a stereo split (the local file stays microphone only). The recorder takes what the call port *receives*, so a tone sent into the port alone would reach the far end but not the file; the direct connection to the recorder is what puts the beep into the recording. `TonePlayer.setSinks` keeps exactly that set: it disconnects sinks no longer wanted and connects wanted ones that were never requested or that PJSIP does not list any more (the port behind them was replaced after a re-INVITE). Runs at the end of every `reconcileMedia`; a recording that moved to another leg (`rehomeRecordings`) gets a new player and a new timer; `finishRecorder` removes both.
- **Timer.** An actor task per recording (`noticeTimers`): sleeps one second, then beeps (`cpjsua_tone_sequence_play_once`, one non-looping `pjmedia_tonegen_play`) and sleeps the interval until the recording is over; cancelled with the player. `setRecordingNotice` works before `start`; a change applies to recordings in progress (players and timers are made again with the new interval; off removes them).
- **Tests.** `recordingNoticeBeepsForBothSidesAndTheFile` (loopback, interval shortened to 0.4 s): a mono recording of the calling leg has 1400 Hz (amplitude > 300), the far leg's port receives level > 10 and the speaker slot too, the player has exactly three sinks including slot 0; a stereo split puts the beep into the remote file (> 300) and not into the local one (< 30); off: a new recording has no player and no beep; switched on during a recording the beep starts without restarting it; hang-up leaves no players or timers.

## Voicemail indicator (MWI)
Code: `VoicemailIndicator.swift` (`MessageSummary` parser, `voicemailState(for:)`), `pjOnMwiInfo` and the voicemail map in `EngineBridge.swift`, `AccountMapping` (`mwiEnabled`), C helper `cpjsua_mwi_body`. Model: `AccountConfig.mwi` (default true; missing in older JSON decodes as true) and `AccountConfig.voicemailNumber` (nil; the UI dials it, the engine does not use it).

- **Subscription.** `pjsua_acc_config.mwi_enabled` follows `AccountConfig.mwi`. pjsua SUBSCRIBEs to the `message-summary` event package at the account's own address once REGISTER succeeds (and again after `updateAccount` switches it on; `pjsua_acc_modify` handles the change) with the default `mwi_expires` (3600 s) and refreshes it; a 489 or 403 from a server without voicemail is only logged by pjsua. Unsolicited NOTIFYs (servers that push message-summary without a subscription, as Asterisk can) are accepted too: pjsua's `enable_unsolicited_mwi` stays at its default, pjsua answers 200 and routes the NOTIFY to the account that matches the To header (the default account otherwise), so an account with `mwi == false` still gets an indicator from such a server.
- **Parsing.** `on_mwi_info` copies the NOTIFY body (`cpjsua_mwi_body`, up to 4 KB) and `MessageSummary.parse` reads `Messages-Waiting: yes|no` and `Voice-Message: new/old (urgent new/urgent old)` (case-insensitive names, CRLF or LF, blanks anywhere; other classes such as `Fax-Message` are ignored; without a `Messages-Waiting` line the indicator is on when new messages are counted; a NOTIFY without a body is logged at level 4 and ignored).
- **Events and state.** The bridge keeps the latest `VoicemailState` per account and emits `.voicemail(id, waiting:, new:, old:)` when it differs from the previous one (so the first NOTIFY always produces an event, a refresh with the same numbers does not); every NOTIFY writes a level 4 `.log` line. `voicemailState(for:)` returns the latest value (with the urgent counts), nil before the first NOTIFY, after `removeAccount` and after `stop`. The UI shows the indicator from the event or the snapshot and dials `voicemailNumber` on request.
- **Tests.** `voicemailIndicatorSubscribesAndParsesNotify` (`RegistrarStub` answering REGISTER 200 with Expires; the account's registrar and outbound proxy point at it): an account with `mwi` sends a SUBSCRIBE with `Event: message-summary` after registering, an account without `mwi` sends none; an unsolicited NOTIFY from the stub's socket (no To tag, `Subscription-State: active`, body with `2/5 (1/0)`) produces one `.voicemail` for the right account and the snapshot with urgent counts, the same NOTIFY again produces nothing, a `no` / `0/7` NOTIFY produces the second event, `removeAccount` clears the snapshot. `messageSummaryParsing` (pure), `accountConfigDecodesVoicemailDefaults`, the `mwiEnabled` round trip in `accountConfigMapping`.

## Sound events
Code: `Engine+Sounds.swift` (`playEventSound`, `EventSounds`). Settings: `AppSettings.audio.soundEvents` (`SoundEventSettings`: `callEvents`, `keyPress`, `voicemail`, `error`, all false; missing keys decode as false). The engine plays what it is asked; the app decides from the settings when to call it.

- **Sounds** (`SoundEvent`), each one to three beeps under 400 ms at about -15 dBFS: `.callConnected` 660 Hz 80 ms, 880 Hz 120 ms; `.callEnded` 660 Hz 80 ms, 440 Hz 160 ms; `.voicemail` 880, 880, 1175 Hz (70, 70, 120 ms); `.error` 330 Hz 120 ms twice; `.keyPress(digit)` the DTMF pair of 0-9, *, #, A-D for 120 ms (`pjmedia_tonegen_play_digits`; another character throws `.invalidArgument`).
- **Playback.** Each call makes a short-lived `TonePlayer` with an idle tone generator on slot 0 (the call output device; never a call port, never a recorder), queues the sequence once (`cpjsua_tone_sequence_play_once`) and an actor task destroys the player 150 ms after the sound's length. Sounds overlap when asked for together. `stop()` removes players still playing.
- **Tests.** `testToneAndEventSounds`: `.error` and `.keyPress("5")` together give two players and a speaker level > 10, both gone within 2 s; during a connected, recorded loopback call the far leg's recording has no 330, 1336 or 880 Hz from the sounds (amplitude < 30); `.keyPress("x")` throws; every sequence is at most 400 ms (`holdMelodyAndSoundsFitTheGenerator`).
